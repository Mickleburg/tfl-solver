# Проверка provider перед OpenCode smoke

## Цель

Понять, был ли прежний `503` следствием параллельных model calls либо ошибкой
нового педагогического промпта. Репозиторий находился на commit `827727c` с
revision 8: один model call и четыре последовательных этапа внутри него.

## Наблюдения

- Долгоживущий процесс OpenCode пользователя не завершался и не изменялся.
- `pt/positive-llm-qwen36` не вернул минимальный ответ `OK` за 90 секунд.
- `pt/positive-llm-chat` не вернул тот же минимальный ответ за 90 секунд.
- HTTPS-запрос без ключей к `api-llm.ptsecurity.com/v1/chat/completions` не
  установил соединение за 20 секунд.

## Вывод

Гипотеза о прежнем конфликте параллельных запросов правдоподобна, но текущая
недоступность шире одной модели и возникает до выполнения инструкции агента.
Поэтому содержательный revision-8 smoke не запускался: он не дал бы данных о
математике, JSON Schema или числе инструментов.

Повторять нужно в окно, когда короткий запрос получает ответ. Открытый UI сам
по себе не считается конфликтом; важно отсутствие другой активной генерации.
После успешного health-check запускается ровно один случай
`training-unbounded-delay`, а не полный набор.
