# Проверка provider перед OpenCode smoke

## Цель

Понять, был ли прежний `503` следствием параллельных model calls либо ошибкой
нового педагогического промпта. Репозиторий находился на commit `827727c` с
revision 8: один model call и четыре последовательных этапа внутри него.

## Наблюдения

- Долгоживущий процесс OpenCode пользователя не завершался и не изменялся.
- `pt/positive-llm-qwen36` не вернул минимальный ответ `OK` за 90 секунд.
- `pt/positive-llm-chat` не вернул тот же минимальный ответ за 90 секунд.
- HTTPS-запрос без ключей к `api-llm.ptsecurity.com/v1/chat/completions` не
  установил соединение за 20 секунд.

## Вывод

Первичная гипотеза о внешней недоступности оказалась неполной. Сравнение
окружений показало, что работающий интерактивный OpenCode и `bash -ic`
получают `LLM_API_KEY` из существующего `~/.config/opencode/pt.env`, а прямой
вызов через `wsl --cd` эту часть `.bashrc` не исполняет. Глобальная
конфигурация OpenCode исправна и не изменялась.

Минимальный запрос через `bash -ic` вернул `OK`, после чего revision-8 smoke
был выполнен. Открытый UI сам по себе не оказался препятствием; для запуска из
Windows важно входить через интерактивную оболочку и не выводить значение
секрета в диагностику. Результат содержательного запуска вынесен в отдельный
отчёт `opencode-qwen36-revision8-smoke-2026-09-29.md`.
