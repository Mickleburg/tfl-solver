# OpenCode и локальные модели

OpenCode использует уже существующий адаптер
`.agents/skills/tfl-solver/SKILL.md`: отдельная копия предметных инструкций не
нужна. По официальному контракту OpenCode ищет project skills в
`.agents/skills/*/SKILL.md`, а модель для одного запуска задаётся как
`provider/model`.

Текущая проверенная версия клиента в WSL Debian — 1.18.34.

## Обычная работа

В Debian открой корень репозитория:

```bash
cd ~/Projects/tfl-solver
opencode .
```

Сформулируй задачу обычным языком или явно попроси загрузить skill
`tfl-solver`. `AGENTS.md`, канонический skill, корпус и Python-оракулы остаются
теми же, что в Codex и Claude Code.

### Изолированный клон в WSL

Для Debian клон размещается в `~/Projects/tfl-solver`. Личный GitHub не должен
менять рабочую конфигурацию GitLab: отдельный ключ хранится в
`~/Projects/.ssh/github_personal_ed25519`, а `user.name`, `user.email`,
`core.sshCommand` и SSH-адрес `origin` задаются в локальном `.git/config`
клона. Глобальные Git- и OpenCode-конфиги при этом не изменяются.

После создания ключа его открытая часть добавляется в личный GitHub. Проверка
доступа и обновление клона выполняются уже из `~/Projects/tfl-solver`:

```bash
ssh -T -i ~/Projects/.ssh/github_personal_ed25519 \
  -o IdentitiesOnly=yes git@github.com
git fetch origin
```

Для текущего изолированного клона обе команды проверены: GitHub распознаёт
аккаунт, а `fetch` и `pull` работают через локальный `core.sshCommand`, не
затрагивая глобальную конфигурацию Debian.

Доступные модели нужно узнавать у самого клиента, не угадывать по имени:

```bash
opencode models
```

Текущий provider читает ключ из переменной `LLM_API_KEY`. Она загружается
существующим `.bashrc` из `~/.config/opencode/pt.env`; значение ключа не
хранится в репозитории. Поэтому прямой неинтерактивный вызов вида
`wsl -d Debian --cd ... opencode ...` неэквивалентен обычному запуску в
терминале: он не читает эту часть `.bashrc`. Для автоматического вызова из
Windows используется интерактивная оболочка:

```powershell
wsl -d Debian --exec bash -ic "cd ~/Projects/tfl-solver; opencode models"
```

OpenCode поддерживает локальные OpenAI-совместимые серверы и Ollama. Конкретный
provider и model ID настраиваются пользователем в OpenCode; репозиторий не
фиксирует модель и не хранит ключи доступа. Официальные инструкции:

- <https://opencode.ai/docs/providers/>;
- <https://opencode.ai/docs/models/>;
- <https://opencode.ai/docs/skills>.

## Измеримый smoke для слабой модели

Сначала запускается один тренировочный случай:

```bash
python3 -m tfl pedagogy run \
  --runner opencode \
  --model pt/positive-llm-qwen36 \
  --case training-unbounded-delay \
  --timeout 900 \
  --output ~/Projects/tfl-eval-runs/opencode-smoke.jsonl
```

После ручной проверки математики можно запускать остальные случаи. Для
OpenCode используется `.opencode/agents/tfl-eval.md`: он запрещает изменение
репозитория, сеть и подагентов, разрешая Python-проверки. Перед вызовом модели
runner сам выполняет детерминированный intake и передаёт одну подходящую
семинарскую карточку, её предпосылки, путь открытия и команду оракула. Поэтому
модель не расходует вызовы на повторное чтение skill, индекса и рецепта.
Runner читает JSONL-события `tool_use`, `text` и `step_finish`, поэтому scorer
видит реальные вызовы оракулов и расход токенов.

Полный набор не следует запускать первым: Codex baseline потребовал более
миллиона входных токенов даже с кэшированием. На локальной модели сначала нужно
измерить один случай, затем исправлять только наблюдаемые сбои. Если tool calls
обрываются, официальный provider guide рекомендует проверить размер контекста;
для Ollama отправная точка — 16–32K.

## Граница текущей проверки

Адаптер, JSONL-parser, схема ответа и read-only профиль покрыты unit-тестами.
В WSL Debian найден OpenCode 1.18.32 и выполнен реальный smoke на
`pt/positive-llm-qwen36`. Модель дала правильный итог, но сделала ложное
промежуточное наблюдение и использовала 20 вызовов вместо 8. Рубрика revision 6
отдельно ловит содержательную ошибку пути и превышение бюджета; результат не
маскируется как PASS. Подробности — в отчёте
`reports/pedagogy/opencode-qwen36-smoke-2026-09-28.md`.

В revision 7 поиск аналога вынесен в проверяемый intake-пакет. Новый smoke
должен отдельно подтвердить, что это сокращает маршрут и не скрывает
математические ошибки модели; старые два запуска остаются отрицательным
baseline revision 6.

Первая попытка revision 7 не дошла до модели: provider вернул `503` после
491,76 секунды, а короткий запрос без инструментов также не ответил. Это
зафиксировано как внешний сбой, не как содержательный FAIL. Повтор нужен после
восстановления provider; подробности — в отчёте
`reports/pedagogy/opencode-qwen36-revision7-smoke-2026-09-28.md`.
Scorer выводит для таких записей отдельный статус `INFRA ERROR` и считает их
отдельно от содержательных результатов модели.

Revision 8 декомпозировала работу внутри одного model call: сверка предпосылок
без инструментов → один оракул → общее доказательство → проверка типов JSON.
Отдельные model calls и подагенты для этих этапов не создаются: это сохраняет
контекст и не усиливает ограничение provider на параллельные запросы.

После запуска через корректно инициализированную интерактивную оболочку
revision 8 получила содержательный результат 8/13. Модель вызвала нужный
оракул и пришла к правильному общему итогу, но затем сделала две лишние
Python-проверки сериализации и подменила параметрическое семейство общих
префиксов ложным утверждением о росте остатков Сардинаса—Паттерсона. Полный
разбор находится в
`reports/pedagogy/opencode-qwen36-revision8-smoke-2026-09-29.md`.

Revision 12 передаёт модели явное семейство `xz^k` и `yz^(k-1)`, ограничивает
бюджет двумя командами, запрещает отдельную инструментальную сериализацию,
размещает Schema до условия и требует точно переносить малые приёмы и результат
оракула. Контрольный smoke прошёл 13/13 за 62,83 с с одним Python-вызовом;
математика проверена вручную. Подробности — в отчёте
`reports/pedagogy/opencode-qwen36-revision12-smoke-2026-09-29.md`.

Последовательный baseline завершён на рубрике revision 37. Все восемь случаев
получили PASS, суммарный балл — 103/104, каждый выбранный результат использовал
ровно один Python-вызов. Семь training-случаев и один full-случай проверены
вручную; суммарное время выбранных запусков — 368,864 с. Первый запуск
последнего full-случая не вернул структурированный финальный объект после
правильной команды, повтор на том же коммите прошёл. Это отдельно учитывается
как сбой сериализации, а не как математический ответ. Сводка и границы
результата находятся в
`reports/pedagogy/opencode-qwen36-baseline-revision37-2026-10-05.md`.

Перед дорогим smoke нужно дождаться завершения других активных генераций и
проверить выбранную модель минимальным запросом. Сам открытый процесс/UI
OpenCode не обязательно занимает model slot. Если минимальный запрос не
отвечает, сначала нужно проверить, получил ли процесс `LLM_API_KEY` через
интерактивную инициализацию shell. Только подтверждённый сетевой или provider-
сбой следует отделять от ошибки модели. Диагностика 2026-09-29 находится в
`reports/pedagogy/opencode-provider-check-2026-09-29.md`.
